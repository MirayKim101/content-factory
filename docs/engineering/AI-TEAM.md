# Content Factory — AI-команда разработки

Статус: действующий регламент
Дата: 2026-09-01

## Зачем нужна команда

AI-команда помогает владельцу разрабатывать Content Factory, но не является
частью runtime самого продукта. Внешний AI-сервис поиска вертикальных клипов —
отдельная продуктовая интеграция, которая появится на третьем этапе MVP.

## Состав

| Роль                   | Где находится                  | Когда используется                                                                                  |
| ---------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------- |
| Manager / orchestrator | основной чат Codex             | всегда; принимает задачу и собирает результат                                                       |
| Architect              | `.codex/agents/architect.toml` | существенные изменения API-совместимости, persistence model, очереди, state machine, ADR и baseline |
| Frontend               | `.codex/agents/frontend.toml`  | Nuxt/Vue, формы, статусы, админка и браузерные сценарии                                             |
| Backend                | `.codex/agents/backend.toml`   | NestJS, PostgreSQL, BullMQ, воркеры, FFmpeg и интеграции                                            |
| QA                     | `.codex/agents/qa.toml`        | тестовые сценарии, controlled failures и воспроизводимые проверки                                   |
| DevOps                 | `.codex/agents/devops.toml`    | Docker Compose, CI/CD, deployment и observability                                                   |
| Reviewer               | `.codex/agents/reviewer.toml`  | независимая финальная проверка каждого изменения                                                    |

Роли существуют постоянно как доступные специализации, но не запускаются все
на каждую задачу.

## Базовая схема работы

Для обычного вертикального среза:

```text
Владелец
-> Orchestrator
-> один Implementer
-> QA при необходимости
-> независимый Reviewer
-> Orchestrator
-> пошаговый результат владельцу
```

Architect добавляется перед Implementer, если задача существенно меняет
архитектурный baseline, совместимость API, persistence model, границы модулей,
тип очереди, deployment topology или архитектурный стиль. Обычные новые
endpoint, таблица или job внутри уже одобренного baseline не требуют отдельного
ADR. DevOps добавляется только для инфраструктурной части.

## Почему не запускаем всех одновременно

На раннем MVP frontend, backend, схема базы, OpenAPI и lockfile часто меняются
одной задачей. Несколько пишущих агентов создадут конфликт и потерю контекста.
Поэтому один implementer владеет одним сквозным сценарием. Параллельно можно
делегировать независимое чтение, исследование официальной документации или
review, но не пересекающиеся изменения общих файлов.

## Протокол постановки задачи

Перед делегированием orchestrator создаёт task brief по шаблону
`docs/engineering/TASK-BRIEF.md` и указывает:

1. наблюдаемую цель для пользователя;
2. что точно не входит в задачу;
3. критерии приёмки;
4. разрешённые и запрещённые файлы;
5. обязательные документы;
6. команды проверки;
7. failure behavior;
8. rollback.

Агент не расширяет задачу самостоятельно. Материальный конфликт возвращается
orchestrator, а архитектурный конфликт — architect.

## Quality gates

### Для каждого изменения

- форматирование и lint;
- strict typecheck;
- релевантные unit и integration tests;
- contract check при изменении API;
- пользовательский smoke-сценарий;
- минимум один контролируемый ошибочный сценарий;
- структурированные логи или другое воспроизводимое evidence;
- синхронизация документации;
- понятный rollback.

### Для фоновых заданий

- версия job payload;
- idempotency key;
- timeout;
- retry и backoff;
- терминальная ошибка;
- progress и correlation ID;
- безопасный restart;
- восстановление задания из PostgreSQL;
- очистка временных файлов;
- защита от повторного результата или публикации.

### Для FFmpeg

- ffprobe входного и выходного файла;
- проверка длительности результата в заданном допуске;
- воспроизводимый MP4;
- checksum и lineage;
- версия FFmpeg и рецепта;
- controlled failure для повреждённого файла;
- controlled failure для неверных таймкодов.

## Независимый review

Автор изменения не может быть его единственным reviewer. Reviewer:

1. самостоятельно читает критерии приёмки;
2. смотрит фактический diff;
3. повторяет команды проверки;
4. проверяет happy path и failure path;
5. сообщает замечания с файлом, строкой и способом воспроизведения;
6. после исправлений выполняет re-check.

Отчёт implementer без повторяемых команд и наблюдаемого результата не является
доказательством готовности.

## Границы безопасности

- Папки `seanova` и `dockerServer` полностью исключены из работы команды.
- Внешние записи, публикации, покупки и разрушительные операции требуют
  соответствующего разрешения владельца.
- Секреты не коммитятся и не выводятся в логи.
- Источник видео для тестов должен быть собственным или явно разрешённым.
