## Следующий запуск восстановленной версии

Запуск данных — отдельная следующая задача, не выполненная этим Git merge.
Исполнитель должен подготовить и проверить конкретную изолированную среду:

1. Отдельный Compose project и network, например `content-factory-restored`,
   отдельные volumes и свободные loopback ports. Одного `-p` недостаточно без
   изменения явного network name из базового Compose.
2. Новый `.env` с новыми credentials, отдельной пустой PostgreSQL database,
   новым private S3 bucket/prefix namespace и отдельным `MEDIA_QUEUE_NAME`.
   Не использовать старый env или Mac credentials как shortcut.
3. Проверить `docker compose ... config --quiet`, затем запустить только новые
   PostgreSQL/Redis/MinIO и provisioning. Сначала применить восстановленную
   последовательность миграций к **пустой** новой базе, затем включать worker/API.
4. Сохранить `AI_CONTEXT_ENABLED=0`, пока отдельная frontend приёмка Stage 2B-1
   не выполнена. Export/assembly admission включать по их rollout instructions,
   а не по факту наличия исходников.
5. Проверить ручной Stage 2 на synthetic media и только потом восстанавливать
   пользовательские данные из доказанно совместимого Mac backup, если он есть.

Владелец не обязан вручную собирать эту конфигурацию. Эти пункты — точная задача
следующего автономного запуска. Совместимая Mac-база и media storage пока не
восстановлены. Для переноса WSL-created projects нужен отдельный reviewed ETL;
переписывать `_prisma_migrations` или накатывать Mac migrations поверх WSL нельзя.

## Откат к прежней WSL-реконструкции

Переключить Git на `recovery/linux-mvp-20260909`, восстановить его зависимости и
сборку. Только после сверки выбранной схемы вернуть сохранённый env и запускать
старые процессы с прежним Compose. Новую базу не откатывать старым dump поверх
более свежих записей. Истории обеих реализаций сохранены в Git.

Каталоги Seanova и DockerServer в любом регистре и связанные ресурсы остаются
полностью вне области работы, независимо от полного доступа.
